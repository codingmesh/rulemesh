# 软件工程质量评估依据与 RuleMesh 评估方法

调研日期：2026-10-12。范围：公开的一手标准摘要、原作者论文与工程实践。本文件给出评估依据与项目建议，**不是当前代码的验收报告，也不是 ISO 认证或符合性声明**。没有阅读 ISO/IEC 25010、25023 的完整付费正文；下述 ISO 结论限定于官方公开摘要和状态页。

## 1. 调研结论

软件质量需要以项目目标、质量属性、实际行为和变更证据综合评价。测试通过、lint 无错误、目录分层、应用某个设计模式，分别只能支持有限结论，不能单独证明代码高质量、架构合理或易扩展。架构应按明确场景评价；代码评审还要审查设计、复杂度及故障路径。这里采用 ISO 的质量模型与测量边界、Google 的评审方法、SEI 的场景方法及经典模块化原则，而不拼装一个缺乏依据的总分。

## 2. 质量模型与测量标准

### ISO/IEC 25010:2023：规定评价什么

2023 年第 2 版定义 ICT 与软件产品质量模型，包含**九项特征**及子特征，用于需求、设计目标、测试目标和验收准则。官方页面显示其为已发布版本，2011 版已撤销。因此不能把网上常见的 2011 年八特征列表当成 2023 模型。公开摘要未逐项列出全部特征，本调研不凭二手转载复述完整条款。模型覆盖产品质量，并不等同于只评价代码格式。[ISO 官方摘要与版本状态](https://www.iso.org/standard/78176.html)、[IEC 官方产品页](https://webstore.iec.ch/en/publication/90024)

### ISO/IEC 25023:2016：规定如何量化，而不替项目决定阈值

该标准提供产品质量度量及其应用说明。官方明确说明：**不把度量值统一对应到等级或符合性分数**；范围取决于产品性质、软件类别及用户需求。2016 版当前仍为已发布版本，但处于修订阶段，页面列出下一版草案 ISO/IEC DIS 25000-23.2。不能将草案当作已发布标准，也不能把本项目自定的复杂度、覆盖率阈值称为 ISO 要求。[ISO 官方摘要、状态与下一版草案](https://www.iso.org/standard/35747.html)

### ISO/IEC 5055:2021 / CISQ：检查结构性风险

5055 通过源代码中架构和编码实践的严重违规来衡量风险。CISQ 将其分为可靠性、安全、性能效率和可维护性，强调需要看组件之间的连接。2021 版 ISO 页面当前显示已发布，并处于系统评审阶段；不是已经撤销或已由新版替代。资源释放、错误处理及跨层依赖都属于值得检查的结构问题，普通格式 lint 不能替代这类分析。[ISO 官方摘要与状态](https://www.iso.org/standard/80623.html)、[CISQ 原始说明](https://www.it-cisq.org/standards/code-quality-standards/)

可公开读取的 OMG ASCQM 1.0 正文包含结构弱点及检测规范；本调研只查看范围和相关索引，未执行其完整度量算法。CISQ 页面还保留 ISO 25010 的旧八特征表述，应识别其年代，不能据此否定 25010:2023 的九特征模型。[OMG ASCQM 1.0 规范](https://www.omg.org/spec/ASCQM/1.0/PDF)

## 3. 代码质量与设计原则如何评审

### Google Engineering Practices：检查设计和行为，而不只检查工具输出

Google 的评审维度包括整体设计、功能、复杂度、测试、命名、注释、风格和文档。评审者应思考边界情况及并发问题；测试自身也须审查是否合理、有用。其复杂度指南明确反对为尚未发生的需求提前加入泛化机制。评审准入关注持续改善代码健康，而不是要求绝对完美。[评审检查项](https://google.github.io/eng-practices/review/reviewer/looking-for.html)、[评审准入标准](https://google.github.io/eng-practices/review/reviewer/standard.html)

**项目应用建议：**查看真实调用链、失败传播、资源所有权和契约；衡量测试能否拦截错误行为。测试数量只作记录，覆盖率、复杂度、文件大小仅作定位风险的信号，不作为单独验收结论。

### 模块化、SOLID 与依赖原则：以变更影响证明收益

Parnas 主张模块应隐藏困难或可能变化的设计决策，而不只是按处理步骤切文件。Martin 对 SRP 的解释强调将同一变化原因的内容放在一起、将不同变化原因的内容分开；因此“一函数一个文件”并不等于单一职责。[Parnas 原始论文](https://www.cs.lafayette.edu/~gexia/cs301/resources/parnas.html)、[Martin 对 SRP 的解释](https://blog.cleancoder.com/uncle-bob/2014/05/08/SingleReponsibilityPrinciple.html)

开闭原则关注通过明确扩展位置加入行为；它不要求永远不修改已有代码。依赖规则强调高层策略不依赖外层实现细节，但也不强制复制完整的四圈架构。小型构建项目可以用函数、数据和既有策略接口表达边界，无须为每层增加 service、provider 或 interface。[Martin 对 OCP 的说明](https://blog.cleancoder.com/uncle-bob/2014/05/12/TheOpenClosedPrinciple.html)、[Martin 的依赖规则与边界数据](https://blog.cleancoder.com/uncle-bob/2012/08/13/the-clean-architecture.html)

Liskov 与 Wing 的行为子类型要求关注调用者可依赖的契约及不变量；签名能通过类型检查，不代表实现可替换。对于 writer/worker，需要检查相同输入语义、错误传播与副作用，而不是只检查继承关系。[Liskov / Wing 原论文](https://www.cs.cmu.edu/~wing/publications/LiskovWing94.pdf)

**项目应用建议：**不以“用了 Strategy”“符合 SOLID”的标签验收。只对实际使用到的原则提供证据：谁因什么需求而变化、变化是否局部、依赖是否逆向、替换实现是否保持契约、不必要的抽象是否被删除。无适用对象的原则记为不适用并说明理由。

## 4. 架构质量要用场景表达

SEI 用质量属性场景描述来源、刺激、环境、被影响对象、响应及响应度量。可修改性等需求会影响架构；架构机制须结合目标与权衡来分析，而不是凭目录图断言合理。其场景分析也可以记录实现变化的工作量和受影响子系统。[SEI：质量属性推理](https://www.sei.cmu.edu/library/reasoning-about-software-quality-attributes/)、[SEI：架构策略与六要素场景](https://resources.sei.cmu.edu/asset_files/TechnicalReport/2003_005_001_14213.pdf)

以下是**本项目建议的场景**，不是标准规定的通用阈值：

| 目标 | 场景 | 可观察证据与通过条件 |
| --- | --- | --- |
| 规则维护 | 维护者添加一个已有类别的域名与一条例外 | 修改声明数据即可；原顺序、优先级及四端行为保持契约；无需修改客户端渲染算法 |
| 来源扩展 | 新增一种真实需要的来源格式 | 影响集中在来源解析及注册位置；不要求各 writer、配置与页面重复适配 |
| 客户端扩展 | 支持一种确有需求的新客户端格式 | 可明确列出 writer、客户端交付定义、能力及验证的修改位置；不改既有解析语义或复制规则主数据 |
| 可靠性 | 并发 writer 失败，其他任务仍在运行 | 等待已启动工作收尾；保留原错误；失败后无晚到写入、假成功或资源残留 |
| 完整性与安全 | 输出路径误设，缓存内容损坏 | 危险目录在 IO 前拒绝；损坏缓存不改变规则；有效源数据保持完整 |
| 构建一致性 | 同输入冷/热构建与同进程再次调用 | 除已明确批准的非语义元数据外产物一致；缓存状态及运行顺序不改变语义 |
| 可分析性 | 未参与实现者定位一次失败 | 能从输入来源、错误链和模块接口定位原因；实际阅读范围、问题与耗时作为证据记录 |

扩展场景可以先做只读变更影响分析；若声称“扩展已验证”，则应有一个临时、不合入生产的代表性变更及回归结果。记录触及的职责、依赖和重复知识，不把任意“最多改几个文件”设成硬门槛。不得为了证明扩展能力给生产代码加入测试专用接口。

## 5. 交付过程指标不能替代源码质量

DORA 当前使用五项软件交付表现指标，分别覆盖吞吐与不稳定性：变更前置时间、部署频率、失败部署恢复时间、变更失败率、部署返工率。它们测量交付过程的结果，应按具体服务的上下文应用。一次修改用时很长或反复返工值得记录和改善，但不是代码质量总分；本项目也无需为了套用指标增加 Release、回滚演练或多版本机制。[DORA 官方指标指南](https://dora.dev/guides/dora-metrics/)

## 6. RuleMesh 的最小评估矩阵

以下为评估方法建议，不对当前实现预先判定通过。每条结论绑定被评审代码版本、检查范围、实际证据和剩余限制；已有证据可复用，只有发生相关变化或证据失效时才重复执行。

| 维度 | 要回答的问题 | 所需证据 |
| --- | --- | --- |
| 功能与语义 | 真实交付规则是否保留匹配、顺序及客户端能力差异？ | 输出语义断言、原生校验、代表性路由及已声明差异 |
| 安全与可靠性 | 路径、故障、资源、并发是否保持契约？ | 危险输入与故障反例；所有 IO 和清理链路审查 |
| 模块与依赖 | 职责是否清楚？事实是否唯一？高层是否依赖入口/页面细节？ | 真实依赖、调用者及重复逻辑清单；反向依赖检查 |
| 可维护性 | 能否理解、定位、修改而不波及无关职责？ | 阅读与诊断记录；规则/来源变更影响分析或实验 |
| 可扩展性 | 新格式/来源是否沿既有边界实现？是否需要复制引擎？ | 代表性扩展实验或明确标记为未实验的影响分析 |
| 简洁性与设计模式 | 抽象是否解决当前问题，收益是否超过额外认知成本？ | 每个机制的实际调用者、替代方案及删除旧逻辑证据 |
| 回归保护 | 测试是否能拒绝坏实现？是否重复或只镜像实现？ | 对关键验收做定向变异/反例验证；风险到检查的映射 |
| 性能与开发效率 | IO、网络、worker、缓存是否必要且有边界？ | 定义输入和环境的耗时/资源记录；仅在真实风险处测量 |

证据强度依次区分：**可复现行为证据**（真实输出/故障/变更实验）、**静态结构证据**（调用链与契约）、**文档声明**（尚未证实）。它们相互补充，不能把最后一项写成前两项。

结论只使用四种状态：**失败**（可复现反例或违反已定契约）、**部分通过**（部分场景已验证）、**通过**（明确范围全部满足并保留限制）、**未测**（证据不足）。关键安全或可靠性失败不能被其他维度平均分抵消。对“易维护、易扩展”的结论必须有变化场景证据；“本轮未发现问题”只描述评审结果，不证明不存在问题。

## 7. 未验证范围

这份研究没有重新运行 RuleMesh 的构建/测试，没有验证之前完成声明，也没有对当前工作树给出架构总验收。正式判断须将本文件的方法应用到实际代码与证据，尤其核对重复知识、全局状态、故障收尾、缓存语义、客户端新增点及代表性修改影响。付费标准完整条款、完整 ISO 5055 自动度量符合性和外部认证均未验证。
