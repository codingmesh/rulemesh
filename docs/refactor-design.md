# RuleMesh 重构方案

版本：1.3。日期：2026-10-12。基线：`ed766d95`。工程结果见[工程验收](engineering-acceptance.md)，规则/配置/分发状态见[项目验收](client-acceptance.md)。手机实机、完整GUI流程与系统扩展连接不是项目完成门槛。

用户最新要求：先规范化、完善工程体系、代码质量和架构设计。本版替代1.0中把工程与未确定客户端产品设计捆绑的实施安排。完整问题证据见[分析](refactor-analysis.md)，工程约定的唯一正文见[engineering.md](engineering.md)，依赖与验收见[任务](refactor-tasks.md)。

用户要求：收益没有达到预期的改法不能采用；按既定职责解决根因，不堆叠补丁。下面的收益准入约束每项改动，不缩减最终项目验收要求。

## 0. 收益准入：通过才采用

每项改动先明确问题及可观察的收益，用基线和必要检查证明后才保留。整体重构完成仍须E12；局部检查通过不能写成整个项目达标。

| 改动 | 必须证明的收益 | 不足以采用的理由 |
| --- | --- | --- |
| 规则正确性 | 同一输入下错误匹配、遗漏或静默成功得到纠正；正常语义保持 | 新增parser、类型或更多测试但没有行为证据 |
| 模块组织 | 真实调用者共享同一实现，旧定义删除，职责和依赖更清楚 | 只搬文件、增加转发层或把一个大文件变成多个相互依赖文件 |
| 客户端事实 | 修改一处定义即可影响实际消费者，路径与动作保持一致 | 多一个registry但页面、CLI仍保留分支副本 |
| 资源收尾 | import无副作用、重复执行有效、失败收尾完整，原始错误保留 | 引入上下文框架但不能完成构建或证明跨次行为 |
| 输出与缓存 | 同输入文件集合正确、删除不残留、历史输入保留且可说明 | 用全局登记机制替换旧流程，却留下历史输入丢失或构建失败 |
| 日常维护 | 同一检查链可运行、来源错误可定位、候选幂等 | 文档承诺更多检查，实际迭代仍重复全量网络构建 |

实施约束：

- 先利用现有FileOutput、任务函数、worker和稳定写入接口；按真实需要修正。不得预先把所有模块接入新上下文、登记或调度机制。
- 上次引入的AsyncLocalStorage、SharedArrayBuffer失败标志及其跨trace/worker/IO的传播方案已撤销；不把这套实现视为后续基座。若确有必要新增跨模块机制，先比较现有参数传递与资源所有权的办法，证明其解决了后者无法合理解决的问题。
- 每项结构改动列出旧调用点、新调用点、删除逻辑和必要验证。没有真实第二调用者或独立职责的抽象不创建；不以净行数、文件数、测试数判定收益。
- 一项改法验证失败，先判断是预期暴露的旧缺陷还是新引入的回归。不得在原因未明确前扩大迁移范围，也不得通过关闭诊断、叠加补丁或改验收标准维持它。
- 无法达到收益条件的改法撤销，保留故障证据，重新选择更直接的实现。测试通过是必要条件，不能代替架构与维护成本判断。
- 源码编辑使用直接文件补丁；命令用于读取、明确恢复及检查，不再用批量文本改写脚本迁移源码。检查按风险选择，不每次修改都执行全量网络构建。

## 1. 当前目标

先让现有项目具备可维护、可验证、可持续扩展的工程结构。保留Sukka的 `Source → FileOutput → writing-strategy → public`；把重复定义、加载副作用、混杂职责、静默失败、不受控产物和低价值验收规范化。

四主端、多仓库设计参考、完整分类、自定义、客户端选择策略和固定站点目标保留。当前不预先决定节点接入新模式、DNS/默认出口、Minimal/Full档位、任意既有配置合并、客户端支持删除。这些产品决策不再阻塞确认过的工程工作。

## 2. 三类改动与约束

| 改动 | 本次如何处理 | 行为要求 |
| --- | --- | --- |
| 结构重构 | 集中客户端事实、抽离library接口、拆分task/渲染/IO、移除import副作用和重复逻辑 | 相同输入保持规则路径、分层、默认策略及有效行为；输出diff可审阅 |
| 已确认正确性问题 | 读取错误传播、关键词白名单、sing-box独立条件、未知类型/错误分类诊断、重复组合/名称冲突等 | 正确意图有回归证据；修复导致的行为变化单独记录，不伪装为纯搬迁 |
| 项目交付核查 | 分类覆盖、冲突顺序、四端配置、自定义维护与固定站点 | 按已有实现和来源核对实际交付，不以设备测试代替；新产品机制须另行确定 |

代码重构只在工程方案确定后执行。当前新增规范不是已经落地的事实，不能立即把README/AGENTS改成完成承诺。

## 3. 核心架构取舍

1. **继承核心直接改进。** 保留FileOutput、trie/CIDR整理、writer fan-out、shared worker、trace及稳定写入；不重建第二模型或通用转换引擎。
2. **接口可直接使用。** library不import任务入口；CLI/build共用配置生成接口，native验证使用实际交付配置。函数定义、获取输入、生成内容、写文件及进程退出有明确责任。
3. **事实唯一。** 客户端静态定义只保存当前实际路径、格式、scheme；routing-profile仍负责策略；worker registry仍负责策略复活。三者不合成mega registry。
4. **职责聚焦。** build-client-config负责编排写出；配置渲染、能力核查与QR/页面分属实际调用模块。build-public保留Sukka树，将配置视图从巨大字符串中抽离，并由同一元数据生成。
5. **诊断在真实语义处。** 原始输入/分发知道被省略的条件，writer差异不再只靠反向读取另一端List。允许的投影与未知类型区别处理，worker结果一致。
6. **IO生命周期明确。** fetch/扫描/线程在任务调用后开始；共享池归本次构建入口所有，任务借用；失败先停止新任务、取消或等待在途任务，再统一关闭。原始错误不被清理错误掩盖，同进程下一次执行使用新资源。
7. **输出集合有依据。** 对本次task/writer真实文件做小型登记，供引用和交付检查；旧数据只按明确的历史输入或缓存合同使用。测速历史及Mock后备参与输入身份，日期/hash复用属于缓存，不引入全量重放平台。
8. **检查分级。** 沿用当前工具链，目标fixture保护语义，临时目录保护IO，native保护目标运行；按改动风险选择检查，不每次改文件都跑全部网络/GUI。

细则及允许依赖见[工程规范](engineering.md)。具体新函数/文件名在实施中按真实调用关系选择，不在方案中预设一串空壳module。

## 5. 构建与一致性口径

同代码、已保存输入和目标格式下：文件集合、规则语义及有意义元数据必须一致；无volatile字段的JSON/config要求字节一致。规则banner仅允许排除明确的Last Updated字段。源版本、许可证和数据来源不能整体按“注释”忽略。

测速历史域名、实际采用的Mock后备字节是具名历史输入，登记来源、hash和必需/可选合同；不属于“不得影响语义”的缓存。旧产物可提供这些已核对输入，但不能决定本次输出集合。下载缓存、hash比较和日期复用才属于缓存。

冷/热比较固定全部人工、固定、动态、历史输入和后备选择，仅改变缓存有无。旧输出中的有效日期可复用，因此不承诺没有相同日期信息的冷/热构建原始字节全等；只排除明确Last Updated字段。历史输入不同所产生的变化另作输入差异解释，不混作纯重构回归。必需历史输入缺失失败，可选按明确合同处理。

动态数据仍允许在已声明任务里刷新，记录实际依赖/输入身份；语义fixture可离线重现。当前不建立每天保存全部第三方网络内容的长期存档系统。

最小产物登记字段以消费者需要为准：relativePath、producer和必要client/category/format/role。输出实际完成后登记；路径重复、缺引用、未注册交付文件失败。校验与发布同份树，不再复制旧public作为隐式主数据。

## 6. 工程任务和验证

任务E01–E12见[任务清单](refactor-tasks.md)。输入清点、模块职责和已确认故障可以独立收敛；不先等待四端设备可用。关键先后仅由真实数据/接口依赖决定。

E01在改实现前固定代表性输入及旧输出/失败结果：用`ed766d95`代码在隔离目录生成，核对输入hash、必要工具身份和比较字段，不使用来源不匹配的本地`public/`作基线。已确认错误同时记录新预期和允许变化范围，不锁死错误行为。此合同的统一细则见[工程规范](engineering.md)。

代码迁移先用这些基线及已有有效回归保护；确认故障用最小fixture锁住；受影响writer跑相关native，build集合变化跑相同全部输入下的clean/warm/删除验证。工程总体集成时统一运行必要全套，不因文案/文件名调整增加浅层测试。

工程完成要验证规范是否实际成立、重复逻辑是否删除、失败是否中止、主线程/worker是否一致、文件集合/引用是否正确。真实客户端安装/独立选节点/更新持久不在结构测试中代填通过。

## 7. 仍保留的产品事项

项目验收须覆盖当前分类、来源与冲突顺序、四端配置及节点底稿接入、自定义和固定站点。已测更新持久写明机制与边界。当前不加入新的机场转换、平台安装、TUN或GUI兼容框架；设备和权限缺失仅影响对应的补充验证。

节点出口由用户选择；规则集继续分组托管；完整config继续引用ruleset；一个站点入口与Sukka展示方式继续保留。不新增第三类产品入口、任意配置自动理解、Release、多版本、私人托管或项目扩展层。
